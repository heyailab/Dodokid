# ADR-006: 内容生命周期状态机与版本化（content_revisions / 回滚 / 并发冲突）

## Status: Accepted (2026-10-02)

## Background

Spec v0.2 §14.2 锁定内容状态机 `draft → in_review → published → archived`（驳回回 draft；归档可回 draft 重新编辑），§6.2 新增 `content_revisions` 集合。验收硬约束：

- AC-09：editor 提交审核 → 状态置 `in_review` 并写入一条 revision
- AC-10：admin 审核通过 → 内容出现在 C 端 `content/list`
- AC-13：下架/归档 → C 端 `content/list` 不再返回
- AC-14：发布/下架/删除等写审计
- AC-15：draft/in_review 对 C 端完全不可见

需要钉死：状态机在代码中的唯一实现位置、revision 快照时机、回滚语义、并发编辑冲突处理。

## Decision

### 1. 状态机：转移表唯一实现（service 层）

```js
// services/admin/content-admin.service.js（唯一出处，路由/controller 不得复制）
const TRANSITIONS = {
  submit:    { from: ['draft'],                     to: 'in_review', role: 'editor' },
  approve:   { from: ['in_review'],                 to: 'published', role: 'admin'  },
  publish:   { from: ['draft'],                     to: 'published', role: 'admin'  }, // 草稿直发（设计契约 3.4d）
  withdraw:  { from: ['in_review'],                 to: 'draft',     role: 'editor' }, // 撤回待审，不产生 revision
  reject:    { from: ['in_review'],                 to: 'draft',     role: 'admin'  },
  unpublish: { from: ['published'],                 to: 'archived',  role: 'admin'  },
  archive:   { from: ['draft','in_review','published'], to: 'archived', role: 'admin' },
  reEdit:    { from: ['archived'],                  to: 'draft',     role: 'editor' }, // PUT 触发
  restore:   { from: ['*'],                         to: 'draft',     role: 'admin'  }, // revision 回滚
};
```

- `unpublish`（下架）与 `archive`（归档）区别：unpublish 仅从 published 收；archive 可从任何活跃状态收（含废弃中的草稿），二者终态同为 archived。
- **publish（草稿直发，设计契约 3.4d）**：`draft → published`，仅 admin，行为与 approve 一致（置 publishedAt、写 action=publish 的 revision 快照、审计 admin.content.publish），仅入参状态不同；须过乐观锁（expectedVersion）。
- **withdraw（撤回待审，设计契约 3.4d）**：`in_review → draft`，editor+（含 admin）。语义为「撤回待审」：不产生新 revision 快照（后续重新 submit 时再快照），清除 reviewerId，审计 admin.content.withdraw。与 reject（admin 专属、带 reason、写快照）区分。
- **重新编辑**：对 archived 内容执行 `PUT /admin/contents/:id` 时自动转移 `archived → draft`（reEdit），无需独立端点——复用 Spec §5.2 已锁定的 PUT，不新增端点。
- 非法转移（如 submit 一个 published）返回 409（code 40900，message 标明当前状态与允许动作）。
- `in_review` 状态下 PUT 编辑被拒绝（409）——审核中内容冻结，只有 reject 或 archive 能解冻，防止「审核的是什么、改完的是另一个」的沉默逻辑错误。

### 2. 版本与乐观锁

- `content_items.version` 为单调递增整数；**任何**写操作（PUT / submit / approve / reject / unpublish / archive / restore）`version += 1`。
- `PUT` 必须携带 `expectedVersion`（openapi 中 required）；后端以原子条件更新（`where: {_id, version: expectedVersion}`）完成 CAS：
  - 匹配 → 更新成功，version+1；
  - 不匹配 → 409，返回服务端当前 version，前端提示「内容已被他人修改，请刷新后重试」。
- admin 后台是内部低并发场景，CAS 足够，不引入锁服务。

### 3. content_revisions 快照与回滚

快照写入时机（对齐 AC-09，宁可多存不可漏存）：

| 事件 | action | 必写 |
|------|--------|------|
| submit（draft→in_review） | submit | 是（AC-09） |
| approve（in_review→published） | approve | 是（发布快照，回滚可回到「上线时」形态） |
| reject（in_review→draft） | reject | 是（reason 存 note） |
| restore（回滚） | restore | 是 |
| PUT 编辑 / reEdit | — | 否（编辑过程频繁，不产生版本噪音；编辑结果由下一次 submit 快照固化） |

- revision 文档 = `{contentId, version, snapshot: <整份 content_items 文档>, action, note, authorId, createdAt}`；`idx_content_version (contentId, version desc, unique)`。
- **回滚 = 前向新版本，不改历史**：`POST /admin/contents/:id/restore/:revisionId` 把目标 revision 的 snapshot 拷回 `content_items`（status 置 draft，version 继续递增），并写一条 action=restore 的 revision。任何历史 revision 永不被覆盖或删除——审计与可追溯性优先。
- 回滚仅 admin（Spec §5.2 锁定）。

### 4. C 端可见性与查询

- C 端 `/content/list|search|{id}` 查询一律带 `status: 'published'` 条件（AC-13/15），由现有 `content.repo.js` 层强制，不依赖调用方自觉。
- 下架/归档即时生效：无 CDN/缓存层面的状态缓存（内容元数据由数据库直出，媒体 URL 为 CDN 静态资源，不受状态影响但引用它的条目已不可见）。

### 5. 删除语义

- `DELETE /admin/contents/:id`（admin only）为硬删除，同时删除该内容的 `media_assets` 绑定关系（itemId 置空，媒体文件不物理删除，可复用），写 `admin.content.delete` 审计。
- `media_assets` 删除前校验：仍被 published 内容引用时返回 409，防止下架静默失图。

## Consequences

正面：
- 转移表单点实现，非法状态转移在构造期即可被穷举测试（每条 from→to 一个用例，含负例）。
- 快照策略（submit/approve 必写）满足 AC-09 与「回到上线时形态」的运营诉求，编辑噪音不进版本历史。
- 前向回滚 + 乐观锁：无锁服务、无历史改写，实现简单且可审计。

负面 / 风险：
- 快照为整文档冗余存储；内容量级（早教内容，千级）下成本可忽略。
- 「归档 → PUT 自动回 draft」是 Spec §14.2「重新编辑」的落库解释，属设计决定而非新增端点；若产品侧期望显式端点，需走 Spec 变更流程（见回传 advisory）。

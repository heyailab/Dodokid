# ADR-005: 运营后台 RBAC 模型与 admin 鉴权隔离

## Status: Accepted (2026-10-02)

## Background

Spec v0.2 引入三角色 `parent / editor / admin`（§14.1 权限矩阵），并要求（§14.5）：

- 后台登录独立于家长登录；`/api/v1/admin/*` 全部经 `adminAuth` + `rbac` 中间件
- editor 调用发布/下架/删用户等 admin-only 能力必须返回 403（AC-11）
- 后台不返回儿童个人可识别信息；发布/下架/删除/改角色必须写审计（AC-14）

现有后端（CloudBase 云函数 `functions/api`）已有家长侧 `auth` 中间件（SMS 登录、JWT）。需要回答：admin 鉴权与家长鉴权如何隔离，权限矩阵如何落到端点级。

## Decision

### 1. 单 users 集合 + role 字段，双 token audience

不新建 ops_users 集合（避免两套用户体系）。`users.role ∈ {parent, editor, admin}`（Spec §6.1 已锁定字段）。

隔离靠 **JWT audience**：

| 侧 | 登录方式 | token audience | 校验中间件 |
|----|----------|----------------|-----------|
| 家长/儿童 App | 手机号 + SMS（现有 `/parent/login`） | `aud: "app"` | `auth`（现有） |
| 运营后台 | 账号(手机号) + 密码（`/admin/auth/login`） | `aud: "admin"` | `adminAuth` + `rbac`（新增） |

- 签发器为同一 JWT 模块，仅 `aud` 与 `role` claim 不同。
- `adminAuth` 中间件三重校验，任一失败返回 401：
  1. `aud === "admin"`（家长 token 携带 `aud: "app"`，永远进不了后台，即使 role 被误改）
  2. `role ∈ {editor, admin}`（parent 不允许）
  3. `users.status === "active"`（禁用即时生效，不依赖 token 过期）
- `rbac(requiredLevel)` 为第二层中间件：`requiredLevel = 'editor' | 'admin'`；`admin` 端点要求 `role === 'admin'`，`editor+` 端点要求 `role ∈ {editor, admin}`。不满足返回 403（AC-11）。

### 2. 端点级权限矩阵（openapi.yaml 中逐一标注 security + 角色）

| requiredLevel | 端点 |
|---------------|------|
| 公开 | POST /admin/auth/login |
| editor+ | /admin/auth/me, /admin/stats, /admin/contents 全部读写与 submit, /admin/contents/:id/revisions, /admin/contents/:id/preview, GET /admin/media, POST /admin/media, GET /admin/media/:id, /admin/categories 读写 |
| admin only | /admin/contents/:id delete + approve + reject + unpublish + archive + restore, /admin/modules 写操作, /admin/categories/:id delete, /admin/media/:id delete, /admin/users 全部, /admin/audit, /admin/settings |
| 备注 | /admin/modules 列表对 editor 开放（编辑内容需要选模块），创建/修改/删除仅 admin |

### 3. 中间件落位与骨架

```
functions/api/middlewares/
├── auth.js        # 现有，aud="app"
├── adminAuth.js   # 新增：校验 aud="admin" + role∈{editor,admin} + status=active
├── rbac.js        # 新增：rbac('editor'|'admin')，读 req.adminUser.role
└── ...
```

```js
// adminAuth.js（示意）
module.exports = async function adminAuth(req, res, next) {
  const claims = verifyJwt(req.headers.authorization);       // 401 on invalid
  if (claims.aud !== 'admin') return fail401(res);
  const user = await usersRepo.findById(claims.sub);         // 不做缓存禁用歧义
  if (!user || user.status !== 'active' || !['editor','admin'].includes(user.role))
    return fail401(res);
  req.adminUser = { id: user._id, role: user.role };
  next();
};

// rbac.js（示意）
module.exports = (level) => (req, res, next) => {
  if (level === 'admin' && req.adminUser.role !== 'admin') return fail403(res);
  next();
};
```

路由挂载（routes.js 只装配）：`router.use('/admin', adminAuth)` 后逐端点挂 `rbac('admin')`；login 端点在 `adminAuth` 之前单独注册。

### 4. 审计联动

- 每个写操作端点的 service 层写 `audit_log`（`actor = req.adminUser.id`，`actorRole = req.adminUser.role`，`before/after` 快照），事件名对齐 Spec §14.4 清单。
- `admin.auth.login` 成功也写审计（含 ip）。

### 5. ops 账号密码

- Spec §7.2 登录表单为账号密码 → `users.passwordHash`（bcrypt，仅 editor/admin 有值，parent 恒为 null）。密码规则 ≥8 位。
- 运营用户由 admin 通过 `PUT /admin/users/:id/role` 提升（parent→editor 需先有密码，建号走独立内部流程，不在 C 端注册链路中）。

## Consequences

正面：
- 家长 token 与后台 token 在密码学层面不可互换（aud 校验），隔离强度高于「只看 role」。
- 权限矩阵直接映射为 `rbac(level)` 一行挂载，端点数增长不增加模型复杂度。
- 禁用用户即时生效（adminAuth 每次查库），符合安全直觉。

负面 / 风险：
- adminAuth 每请求查一次 users 集合，QPS 低（内部后台）可接受；后续可加 60s 级缓存但需权衡禁用即时性。
- parent→editor 的账号开通流程（初始密码设定）本 ADR 仅约定原则，具体发号流程交由 Phase 3 实现并在 Spec 验证步骤中补一条冒烟。
